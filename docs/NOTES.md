*Test Card — browser app turning a show's output map (Resolume/Pixel Peeker/Blend Calc) into per-output test pattern PNGs; the SMPTE RP 219 pattern is measured from ffmpeg, not transcribed*

**PUBLIC since 2026-08-05** — the private-repo statements below are historical; the repo, its Docker packaging and its `/software` page are all live. See [browser tools published](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/project_browser_tools_published.md).

**Test Card** — test patterns for every physical output in a show. React/TS/Vite
static SPA, no backend. `~/Projects/test-card`, MIT, **GitHub PRIVATE** at
`stoatworks-labs/test-card` (created 2026-08-01, branch `main`). **LIVE at
test-card.stoatworks-labs.com** — static-assets Worker, custom domain attached in
`wrangler.toml` as a `**routes**` entry with `custom_domain = true` rather than by
hand in the dashboard, so a fresh deploy cannot come up without the hostname. On
the website (projects.json + `/thumbs/test-card.png`).

Imports a **Resolume advanced output XML**, a **Pixel Peeker interchange JSON**
or a **Blend Calc design JSON**; renders SMPTE RP 219, 75% bars, user grids,
alignment patterns, LED tile maps, solid fields, greyscale and pixel-check as one
PNG per output (ZIP + manifest when several), or as a single **composition
canvas** — play that through Resolume and each output shows its own name, which
is the fastest proof the output map is what you think it is.

**The RP 219 pattern was measured, not transcribed** — free descriptions of the
standard disagree with each other and mostly omit the code values.
`scripts/extract-rp219-reference.py` renders ffmpeg's `smptehdbars` at 4 sizes
(incl. non-16:9 DCI) and run-length analyses it; result committed as JSON so
tests need no ffmpeg. See [ffmpeg test pattern traps](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/reference_ffmpeg_test_pattern_traps.md) for the two
traps that produce plausible-but-wrong output. Model: rows 7/12, 1/12, 1/12,
3/12; columns a=W/8, b=3W/28, closing exactly as 2a+7b=1.

**Colours are computed from R'G'B' through Rec.709, never tabulated** — all 15
land exactly on the measured values, which is itself the proof the measurement
is sound. Only +I and +Q are constants (I/Q-axis signals, not colours, not
derivable).

Deliberate deviation: ffmpeg ceils each bar and dumps the remainder in the last
column, so its right grey block is up to **6px narrower** than its left. This
rounds cumulative boundaries to nearest instead, keeping the pattern symmetric —
an asymmetric test pattern is a defect. Test allows 8px column drift, exact rows.

**Neither sibling's parts library is vendored** ([pixel peeker](https://github.com/stoatworks-labs/pixel-peeker/blob/main/docs/NOTES.md) (`pixel-peeker`),
[blend calc](https://github.com/stoatworks-labs/blend-calc/blob/main/docs/NOTES.md) (`blend-calc`)): a Pixel Peeker *project* file is refused (cabinets are
library refs in mm — use Export→JSON), and Blend Calc's missing projector raster
is asked for. Critical: **Blend Calc never persists its solved overlap** — in
`fit-width` the vertical overlap is computed, shown as "(solved)", and not
written back, so the JSON's value is a stale input. The importer flags the axis.

Every `Output` carries `rasterSource`; **`slice-bounds` means guessed** and stays
badged in UI, warnings and the ZIP manifest — a Resolume screen on a real display
or capture card records an `idHash` but no dimensions.

217 tests, all offline. Importers tested against **real files only** — Arena
7.27.0's own AdvancedOutput.xml + a saved preset, plus exports generated by
running blend-calc's (`BLEND_CALC_XML_OUT`) and pixel-peeker's
(`PP_WRITE_ARTEFACTS`) own suites.

Deliberately no `diag` module (static page, same call as blend-calc); no ZIP64;
store-only ZIP (PNGs are already DEFLATEd) hand-rolled with CRC-32 against the
published vector. Canvas limits are checked before drawing because **browsers
return a blank image over the limit rather than an error** — an 8K wall would
otherwise export a folder of empty PNGs discovered on site.

## 2026-10-20 — scale and novelty patterns, and MP4 loops

Nine new patterns: rulers, banana for scale, life-size dinosaurs, hamster dance,
ocean waves, dinosaur scroll, volcano and comet, broken wall, your image. The
moving ones export as seamless H.264 MP4 loops made in the browser (WebCodecs +
the hand-rolled `src/lib/mp4.ts`). Outputs gained an optional `pitchMm`; Pixel
Peeker's `wall.referencePitchMm` fills it.

What was actually run, in Chrome 152 on this Mac (the app's built-in browser):

- Loops encoded in the page and read back with ffprobe/ffmpeg: High profile, no
  B-frames, BT.709 limited range flagged, frame counts and durations exact.
- 75% bars from full- and legal-range canvases both decode within 1 code value
  of the standard Y′CbCr bar values.
- Ocean, scroll, volcano, hamsters, broken wall: the canvas at t = T is
  pixel-identical to t = 0. In the encoded file the step from the last frame
  back to the first was larger than any other step until the encoder got a
  warm-up second (see AGENTS.md); now it matches the step into other keyframes.
- Spanning across the six-projector Blend Calc fixture: overlaps agree to within
  nine antialiased edge pixels for every surface pattern.
- Real UI: MP4 export of a 1920x1200 output (330 frames incl. warm-up) in 9.8 s,
  Cancel mid-encode, image load and its return after a reload.

An independent review before landing found twelve problems, all fixed the same
day: the volcano's foreground drew different plants on each output of a span;
the broken wall and the env used only the horizontal scale of a stretched
composition region (such outputs are no longer spanned at all); faults were
dealt by list position, so identical outputs broke alike and a tile on a join
got two faults (now keyed on position); encoding crawled in a background tab;
nothing stopped a 9 GB loop; the MP4 button could be double-clicked; the rough
sea dropped a band at the bottom edge and popped one in at the horizon; plus
bitrate-aware levels, the decoder config, ridge and snow shimmer, Clear
everything leaving the image behind, and tiled images as millions of draws.

Played in Resolume the same day (Arena 7.28.1 build 26535, macOS 26.4.1, this
Mac, driven through its REST API on port 8080): ocean, scroll and hamsters at
1920x1080 and an ocean at 3840x2160, 30 fps, 10 s. Arena reads them through
AVFoundation at the right size, 30/1 fps and 10000 ms. Its output snapshot of
frame 0 matched a BT.709 limited-range decode, mean |error| 0.90 code values at
1080p and 0.78 at 4K (BT.601 limited 3.1, BT.709 full 5.5); it runs about 0.5%
bright, its own gain. Its recorder caught 630 consecutive output frames of the
scroll: every source frame once and in order, wraps 297, 298, 299, 0, 1, 2,
exactly 300 output frames apart.

**Arena's H.264 cold-start freeze.** Triggered from disconnected, an H.264 loop
often plays about 0.6 s (frames 17–23) then holds that picture while Arena's
clock runs on, until the first wrap, after which it plays perfectly. Ours froze
8 of 11 times; ffmpeg's `-c copy` rewrap 3/4; libx264 GOP 30 3/4, one keyframe
per loop 2/3, all-intra 2/3. The first trigger in each series never froze. A DXV
encode of the same pictures froze 0 of 3. Arena plays H.264 through AVPlayer,
which reports itself waiting after the seek to 0. Container, bitstream and
keyframe interval are ruled out, so there is nothing to fix in mp4.ts or
video.ts; the docs give the workaround (DXV via Alley, or one run round first).

Arena traps for whoever does this next: its default keyboard map fires clips
from plain keys typed while it is frontmost, and quitting it dropped the SMPTE
input lines from config.xml and wrote the composition size into
SimpleOutput.xml. Back up its Preferences folder first.

Still not run: nothing on a real wall or projector, no other browser.

The art is drawn in code and is original — including the hamsters, which are a
nod to the 1998 page rather than a copy of it.

## 2026-10-20 — video tiles for rasters too big to encode whole

Allan asked for loops too big for the browser to encode to come out as smaller
tiles instead of an error. Measured first, in Chrome 152 on this Mac
(`VideoEncoder.isConfigSupported`): H.264 stops at 36 864 macroblocks a frame,
level 5.1's MaxFS, 4096 x 2304 in any shape and at 60 fps too, on every profile
and with hardware or software preferred. 8192 x 1080 yes; 4096 x 2306 no, and
nor 4080 x 2312, which has fewer pixels than 4096 x 2304 but more macroblocks
(the review caught that I had first called it an area limit). Nothing at 8K. HEVC, VP9 and AV1 all said yes to 8K,
but the muxer only does H.264, and a tile works in any media server.

`planLoop` tries grids in order of tile count times (1 + |ln aspect|), asking
the browser about each tile size, and takes the first it accepts. Ordering by
count alone cut a 16384 x 16384 canvas into 29 slivers 565 px wide, 29 being
prime; now it is 5 x 6. Planning takes 15–110 ms in Chrome. A hand-set bitrate
is shared between tiles by area.

What was run, through the real UI in the app's browser pane (downloads caught
by a local receiver rather than saved): a 7680 x 4320 dinosaur scroll came out
as 2 x 2 tiles of 3840 x 2160, H.264 High, 60 frames, 2.000 s, BT.709 limited,
named and listed in the manifest. Decoded with ffmpeg and stitched, frames 0
and 30 matched `renderOutput` at t = 0 and 1 s to mean |error| 0.54 and 0.53
code values (99th percentile 4 and 3), the same in every tile and in an 8 px
band on each seam as elsewhere. A per-output set (two UHD outputs whole, one 8K
tiled) and a 7680 x 2160 composition (2 x 1, mean |error| 0.61) also worked;
a single UHD output still downloads as a bare MP4. The export carried on with
the pane hidden.

An independent review found two real bugs, both fixed before landing: a
bitrate above every level, or one the encoder refused, was tiled round instead
of reported (1080p at 900 Mb/s came out as two 450 Mb/s halves); and a browser
with no H.264 at that frame rate made the planner ask about every grid, 705
questions per raster per keystroke, before a misleading "will not take". Now
the whole raster is retried at auto bitrate and a 640x360 probe settles "H.264
at all", and grids are asked about on the probe's profile only, skipping any no
smaller than a size already refused. It also found the 1 GB tab limit applied
per output, not per ZIP, which tiling made reachable (three 8K outputs), and a
manifest that could name files the ZIP had renamed; both fixed.

Not run: tiles played together in Resolume or any media server, other
browsers, a tiled broken wall at full length (it is slow by design).

## 2026-10-21 — Halloween: pumpkin patch, spooky forest, haunted house

Allan asked for a Halloween suite: a pumpkin per tile with a few different
faces, a parallax forest with the night sky, witches on broomsticks and bats,
and a haunted house with zombies and skeletons in front and flying vampires
behind, "ideally with some basic animation". All three move.

- **Pumpkin patch** (`pumpkins`): per LED tile like the hamsters. Six faces,
  each with an expression (blink, wink, chomp, squint, gasp, slits); candles
  flicker at about 1.3, 3.1 and 5.3 Hz in whole cycles. It is a still if both
  movements are off or no face is ticked (plain pumpkins), so `isAnimated`
  asks, for a broken wall over it too.
- **Spooky forest** (`spooky-forest`): five parallax layers on
  `layerWidths(scene.speed)`, shared with the dinosaur scroll. Mist is a ridge
  whose period is a third of the world, drifting a whole number of its own
  periods per loop, faded with a gradient. The near trees are 2–2.4 screen
  heights tall so their crowns are out of shot; with crowns in shot they hid
  the sky and the witches.
- **Haunted house** (`haunted-house`): `scene.seed` only. Walkers go one lap of
  `walkLap(world)` per loop. The ghost started in a lit window, where a pale
  sheet on a yellow pane barely showed; it now haunts a dark one with a cold
  light behind it.

Art is polygons in `art/halloween.ts` as before. The walkers share one rig
(`walkPose`) in body heights, y up, with the hip set so the lower foot is on the
ground; the tests hold both to the ground and to one body height through a
stride. Dead trees are cached as `Path2D` (see AGENTS.md).

Run in Chrome 152 in the app's browser pane (pane hidden; frames posted to a
local receiver rather than screenshotted, since a hidden pane's screenshots lag):

- t = 0 and t = T pixel-identical for all three, at 25, 29.97 and 30 fps and
  7 s and 10 s loops; the middle of the loop differs.
- MP4s of all three at 3840 x 2160 through the real **Download MP4 loop**
  button: 300 frames, 10.000 s, H.264 High, BT.709 limited, decoded by ffmpeg.
  Wrap step against every other step (mean |diff| at 960 x 540): house 1.75 vs
  median 1.55 / max 1.91, forest 2.98 vs 3.04 / 3.46, pumpkins 1.32 vs 1.21 /
  1.39. The house took 42 s to export.
- **Download PNG** gives a 3840 x 2160 still of each (Allan asked for stills of
  the moving patterns; the button was already there).
- Spanning, on the six-projector Blend Calc fixture: in the worst overlap at
  most four pixels are more than three code values out for the forest and the
  house, but up to 231 are out by one to three (the dinosaur scroll: 2, the
  volcano: 21). It is not gradient dithering (a gradient drawn on two offset
  canvases matches) and not the cached tree paths (they match too). Not chased
  further: one to three code values in a blend overlap don't show.
- Render time once the trees are cached: 4–15 ms a frame for the forest at
  1080p, 60–100 ms for the house's first frame.

An independent review, which ran the painters through a recording context
(now `test/recording-context.ts`), found one real bug: on a span every output
got the same pumpkin patch, flickering in step, because LED tiles restart at
each output's origin and the pumpkins were keyed on column and row. They are
keyed on surface position now, and two tests fail without that. Also fixed from
it: the tree cache was capped below what a 7680 x 64 forest needs and rebuilt
1,600 paths a frame (the cap now follows the last frame); on a wide span the
walkers were clones in the same place on every output and the flyers crossed
the whole span per loop (both now go round `walkLap`, 1.3 screens); a portrait
output cut the house off at both ends (now held to the width); a stored face
list of unknown names claimed to move; the mist's sample step didn't divide its
period, so its wrap cut it a few pixels differently. The review also asked for
painter-level tests, which `halloween.paint.test.ts` now is.

Not run: Resolume, a real wall, other browsers, a tiled (8K) Halloween loop.

## 2026-10-21 — classic test card

Allan asked for a "Test Card F style" pattern with the Stoatworks logo, an
image of your own or your own text in the middle instead of the picture of the
girl. That picture (and the card) are the BBC's, so this borrows the furniture
of the tradition rather than the card: grey grid, castellations, a big circle,
colour bars, gratings, greyscale steps, corner circles, pixel checkers, an
ident box. Named "Classic test card".

- The centrepiece (`centre.ts`) is shared settings (`settings.centre`) so the
  AV sync pattern can use it too. "Your image" is the same image as the Your
  image pattern; with none chosen it says "No image chosen" rather than
  showing a blank panel.
- The logo is traced to vector (`scripts/trace-logo.py`, see AGENTS.md): the
  biggest brand raster is 400 x 310. The website's 207 px marks were smaller.
- Always full range: it is a card, not a level reference.
- The bars started out the full width of the circle, which clipped the white
  and black bars down to nothing; they're in line with the gratings now, and
  the circle only takes the outer bars' top corners.

Run in Chrome 152: 1920 x 1080, 3840 x 2160, 1080 x 1920, 3840 x 1080,
1280 x 1024, 640 x 360 and 64 x 36, with the logo, text, an image and no image.
14 ms to render at 1080p. Not run: a real display or projector.

## 2026-10-21 — levels check

Allan asked for "a pattern to easily identify a mismatch in levels (limited vs
full range), and ideally, at which end of the chain the mismatch is taking
place". Near-black (2–32) and near-white (223–253) ladders on 0 and 255, 16
and 235 picked out, always full range.

- The direction is readable: a receiver stretching limited to full (crushed)
  makes squares vanish; a sender squashing full to limited (washed out) keeps
  them all and greys the black. Simulated on the rendered pixels with both
  transfer functions to check that's what each looks like.
- The box isn't: one picture can't say which device in a longer chain did it,
  so the card says to look at a monitor partway along. Said so to Allan up front.
- The notes overran the width at 1080p. `fitTextSize` scaled one measurement
  linearly, and macOS's system font isn't linear in size (26 px measured wider
  than 26.4 px; SF changes its spacing between sizes). It now re-measures at the
  size it picks and steps down; the classic card's labels use it too.

Not run: a real chain with each mismatch. That's the obvious next check, with a
GPU set to limited RGB into a monitor set to full and the other way round.
