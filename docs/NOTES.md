*Test Card — browser app turning a show's output map (Resolume/Pixel Peeker/Blend Calc) into per-output test pattern PNGs; the SMPTE RP 219 pattern is measured from ffmpeg, not transcribed*

**PUBLIC since 2026-08-05** — the private-repo statements below are historical; the repo, its Docker packaging and its `/software` page are all live. See [browser tools published](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/project_browser_tools_published.md).

**Test Card** — test patterns for every physical output in a show. React/TS/Vite
static SPA, no backend. `~/Projects/test-card`, MIT, **GitHub PRIVATE** at
`stoatworks-labs/test-card` (created 2026-08-01, branch `main`). **LIVE at
test-card.stoatworks-labs.com** — static-assets Worker, custom domain attached in
`wrangler.toml` as a `**routes**` entry with `custom_domain = true` rather than by
hand in the dashboard, so a fresh deploy cannot come up without the hostname. On
the website (projects.json + `/thumbs/test-card.png`).

Imports a **Resolume advanced output XML**, a **Pixel Peeker interchange JSON**
or a **Blend Calc design JSON**; renders SMPTE RP 219, 75% bars, user grids,
alignment patterns, LED tile maps, solid fields, greyscale and pixel-check as one
PNG per output (ZIP + manifest when several), or as a single **composition
canvas** — play that through Resolume and each output shows its own name, which
is the fastest proof the output map is what you think it is.

**The RP 219 pattern was measured, not transcribed** — free descriptions of the
standard disagree with each other and mostly omit the code values.
`scripts/extract-rp219-reference.py` renders ffmpeg's `smptehdbars` at 4 sizes
(incl. non-16:9 DCI) and run-length analyses it; result committed as JSON so
tests need no ffmpeg. See [ffmpeg test pattern traps](https://github.com/stoatworks-labs/fleet-notes/blob/main/notes/reference_ffmpeg_test_pattern_traps.md) for the two
traps that produce plausible-but-wrong output. Model: rows 7/12, 1/12, 1/12,
3/12; columns a=W/8, b=3W/28, closing exactly as 2a+7b=1.

**Colours are computed from R'G'B' through Rec.709, never tabulated** — all 15
land exactly on the measured values, which is itself the proof the measurement
is sound. Only +I and +Q are constants (I/Q-axis signals, not colours, not
derivable).

Deliberate deviation: ffmpeg ceils each bar and dumps the remainder in the last
column, so its right grey block is up to **6px narrower** than its left. This
rounds cumulative boundaries to nearest instead, keeping the pattern symmetric —
an asymmetric test pattern is a defect. Test allows 8px column drift, exact rows.

**Neither sibling's parts library is vendored** ([pixel peeker](https://github.com/stoatworks-labs/pixel-peeker/blob/main/docs/NOTES.md) (`pixel-peeker`),
[blend calc](https://github.com/stoatworks-labs/blend-calc/blob/main/docs/NOTES.md) (`blend-calc`)): a Pixel Peeker *project* file is refused (cabinets are
library refs in mm — use Export→JSON), and Blend Calc's missing projector raster
is asked for. Critical: **Blend Calc never persists its solved overlap** — in
`fit-width` the vertical overlap is computed, shown as "(solved)", and not
written back, so the JSON's value is a stale input. The importer flags the axis.

Every `Output` carries `rasterSource`; **`slice-bounds` means guessed** and stays
badged in UI, warnings and the ZIP manifest — a Resolume screen on a real display
or capture card records an `idHash` but no dimensions.

217 tests, all offline. Importers tested against **real files only** — Arena
7.27.0's own AdvancedOutput.xml + a saved preset, plus exports generated by
running blend-calc's (`BLEND_CALC_XML_OUT`) and pixel-peeker's
(`PP_WRITE_ARTEFACTS`) own suites.

Deliberately no `diag` module (static page, same call as blend-calc); no ZIP64;
store-only ZIP (PNGs are already DEFLATEd) hand-rolled with CRC-32 against the
published vector. Canvas limits are checked before drawing because **browsers
return a blank image over the limit rather than an error** — an 8K wall would
otherwise export a folder of empty PNGs discovered on site.

## 2026-10-20 — scale and novelty patterns, and MP4 loops

Nine new patterns: rulers, banana for scale, life-size dinosaurs, hamster dance,
ocean waves, dinosaur scroll, volcano and comet, broken wall, your image. The
moving ones export as seamless H.264 MP4 loops made in the browser (WebCodecs +
the hand-rolled `src/lib/mp4.ts`). Outputs gained an optional `pitchMm`; Pixel
Peeker's `wall.referencePitchMm` fills it.

What was actually run, in Chrome 152 on this Mac (the app's built-in browser):

- Loops encoded in the page and read back with ffprobe/ffmpeg: High profile, no
  B-frames, BT.709 limited range flagged, frame counts and durations exact.
- 75% bars from full- and legal-range canvases both decode within 1 code value
  of the standard Y′CbCr bar values.
- Ocean, scroll, volcano, hamsters, broken wall: the canvas at t = T is
  pixel-identical to t = 0. In the encoded file the step from the last frame
  back to the first was larger than any other step until the encoder got a
  warm-up second (see AGENTS.md); now it matches the step into other keyframes.
- Spanning across the six-projector Blend Calc fixture: overlaps agree to within
  nine antialiased edge pixels for every surface pattern.
- Real UI: MP4 export of a 1920x1200 output (330 frames incl. warm-up) in 9.8 s,
  Cancel mid-encode, image load and its return after a reload.

An independent review before landing found twelve problems, all fixed the same
day: the volcano's foreground drew different plants on each output of a span;
the broken wall and the env used only the horizontal scale of a stretched
composition region (such outputs are no longer spanned at all); faults were
dealt by list position, so identical outputs broke alike and a tile on a join
got two faults (now keyed on position); encoding crawled in a background tab;
nothing stopped a 9 GB loop; the MP4 button could be double-clicked; the rough
sea dropped a band at the bottom edge and popped one in at the horizon; plus
bitrate-aware levels, the decoder config, ridge and snow shimmer, Clear
everything leaving the image behind, and tiled images as millions of draws.

Played in Resolume the same day (Arena 7.28.1 build 26535, macOS 26.4.1, this
Mac, driven through its REST API on port 8080): ocean, scroll and hamsters at
1920x1080 and an ocean at 3840x2160, 30 fps, 10 s. Arena reads them through
AVFoundation at the right size, 30/1 fps and 10000 ms. Its output snapshot of
frame 0 matched a BT.709 limited-range decode, mean |error| 0.90 code values at
1080p and 0.78 at 4K (BT.601 limited 3.1, BT.709 full 5.5); it runs about 0.5%
bright, its own gain. Its recorder caught 630 consecutive output frames of the
scroll: every source frame once and in order, wraps 297, 298, 299, 0, 1, 2,
exactly 300 output frames apart.

**Arena's H.264 cold-start freeze.** Triggered from disconnected, an H.264 loop
often plays about 0.6 s (frames 17–23) then holds that picture while Arena's
clock runs on, until the first wrap, after which it plays perfectly. Ours froze
8 of 11 times; ffmpeg's `-c copy` rewrap 3/4; libx264 GOP 30 3/4, one keyframe
per loop 2/3, all-intra 2/3. The first trigger in each series never froze. A DXV
encode of the same pictures froze 0 of 3. Arena plays H.264 through AVPlayer,
which reports itself waiting after the seek to 0. Container, bitstream and
keyframe interval are ruled out, so there is nothing to fix in mp4.ts or
video.ts; the docs give the workaround (DXV via Alley, or one run round first).

Arena traps for whoever does this next: its default keyboard map fires clips
from plain keys typed while it is frontmost, and quitting it dropped the SMPTE
input lines from config.xml and wrote the composition size into
SimpleOutput.xml. Back up its Preferences folder first.

Still not run: nothing on a real wall or projector, no other browser.

The art is drawn in code and is original — including the hamsters, which are a
nod to the 1998 page rather than a copy of it.

## 2026-10-20 — video tiles for rasters too big to encode whole

Allan asked for loops too big for the browser to encode to come out as smaller
tiles instead of an error. Measured first, in Chrome 152 on this Mac
(`VideoEncoder.isConfigSupported`): H.264 stops at 36 864 macroblocks a frame,
level 5.1's MaxFS, 4096 x 2304 in any shape and at 60 fps too, on every profile
and with hardware or software preferred. 8192 x 1080 yes; 4096 x 2306 no, and
nor 4080 x 2312, which has fewer pixels than 4096 x 2304 but more macroblocks
(the review caught that I had first called it an area limit). Nothing at 8K. HEVC, VP9 and AV1 all said yes to 8K,
but the muxer only does H.264, and a tile works in any media server.

`planLoop` tries grids in order of tile count times (1 + |ln aspect|), asking
the browser about each tile size, and takes the first it accepts. Ordering by
count alone cut a 16384 x 16384 canvas into 29 slivers 565 px wide, 29 being
prime; now it is 5 x 6. Planning takes 15–110 ms in Chrome. A hand-set bitrate
is shared between tiles by area.

What was run, through the real UI in the app's browser pane (downloads caught
by a local receiver rather than saved): a 7680 x 4320 dinosaur scroll came out
as 2 x 2 tiles of 3840 x 2160, H.264 High, 60 frames, 2.000 s, BT.709 limited,
named and listed in the manifest. Decoded with ffmpeg and stitched, frames 0
and 30 matched `renderOutput` at t = 0 and 1 s to mean |error| 0.54 and 0.53
code values (99th percentile 4 and 3), the same in every tile and in an 8 px
band on each seam as elsewhere. A per-output set (two UHD outputs whole, one 8K
tiled) and a 7680 x 2160 composition (2 x 1, mean |error| 0.61) also worked;
a single UHD output still downloads as a bare MP4. The export carried on with
the pane hidden.

An independent review found two real bugs, both fixed before landing: a
bitrate above every level, or one the encoder refused, was tiled round instead
of reported (1080p at 900 Mb/s came out as two 450 Mb/s halves); and a browser
with no H.264 at that frame rate made the planner ask about every grid, 705
questions per raster per keystroke, before a misleading "will not take". Now
the whole raster is retried at auto bitrate and a 640x360 probe settles "H.264
at all", and grids are asked about on the probe's profile only, skipping any no
smaller than a size already refused. It also found the 1 GB tab limit applied
per output, not per ZIP, which tiling made reachable (three 8K outputs), and a
manifest that could name files the ZIP had renamed; both fixed.

Not run: tiles played together in Resolume or any media server, other
browsers, a tiled broken wall at full length (it is slow by design).

## 2026-10-21 — AV sync, and sound in the MP4

Allan asked for "an av sync test pattern, again ideally with the stoatworks logo
or a definable alternative". A sync frame once a second (flash, hand at the top,
box 0), boxes -6..+6 lit one per frame either side, the centrepiece in the ring,
and a one-frame 1 kHz beep at -18 dBFS starting on each sync frame's first
sample. Sync frames sit half an interval from the wrap, so the file starts and
ends quiet.

The MP4 writer gained an AAC track (`mp4a`/`esds`, `smhd`, interleaved with the
video in time order) and `audio.ts` encodes it with WebCodecs. Chrome 152 on this
Mac: AAC-LC supported (and Opus). Priming measured with a click: 2112 samples,
the Apple figure. The edit list skips it.

**AVFoundation trimmed it twice.** First export: ffmpeg had every beep within
0.23 ms of its flash, but an AVAssetReader (scratchpad Swift) read them 44 ms
EARLY. With media_time 0 instead, AVFoundation was right and ffmpeg 44 ms late.
An `afconvert` AAC file had the same edit list and read right in both; with its
`roll` sample group disabled, AVFoundation read it early too. So the track now
writes Apple's `sgpd`/`sbgp` roll group, and both agree.

Measured on exports through the real button, 3840 x 2160, 10 s, decoded by
ffmpeg (beep onset at 10% of peak against the first frame whose side panel is
white): 30 fps, beep minus flash +0.10 to +0.23 ms over all ten; 29.97, +0.21
to +0.23; 25, +0.17 to +0.23. AVFoundation, 30 fps with the roll group: beeps at
0.5001, 1.5002 ... 9.5002 s, sync frames at 0.5, 1.5 ... 9.5. One channel's
tone: -17.99 dBFS RMS-as-peak, 1 kHz. First and last 100 ms silent. ffprobe:
both streams start at 0 and last 10.000 s (10.010 at 29.97).

An independent review then found the one thing a single pass can't show: looped
by ffmpeg (`-stream_loop`), the sound drifted later every time round, 4 ms a loop
at 30 fps and 15 ms at 29.97, so a frame out by the fourth. The edit list's end
fell part way through an AAC packet; AVFoundation stops there to the sample,
ffmpeg keeps the whole packet. Fixed by padding the front so priming, padding
and loop end on a packet boundary, and by counting the movie in samples when
there's sound (in milliseconds the duration rounded, and rounding up pulls in a
whole packet). Re-exported at 29.97 through the app: the edit skips 2848
(2112 + 736) and plays 480480 samples, ending on packet 472; ffmpeg +0.21 to
+0.23 ms single pass and +0.225 ms on each of four passes looped; AVFoundation
beeps at 0.5007, 1.5017 ... against sync frames at 0.5005, 1.5015 ... The
review also re-muxed the 25 and 29.97 exports' streams and read them through an
AVAssetReader: +0.2 ms, so the guide's claim for those rates holds. Also from
it: the priming measurement now refuses anything under one packet (a decoder
that trims would otherwise pass), the caption gives the real interval (a 17 s
loop "every 7 s" flashes every 8.5), the pitch is clamped to 100 Hz–10 kHz, and
the sound encode has back-pressure, progress, Cancel and frees its samples.

Not run: Resolume itself, a camera filming a screen, Windows (whose AAC
encoder will prime differently; that's what the measurement is for). A hunch
from the review, unchecked: Windows Media Foundation might ignore the edit
list's start, which would put the sound 44 ms late there.

## 2026-10-24 — live output

Allan asked for a "live output" mode: a button that puts the pattern full screen,
live, on displays he picks. Built as a panel in the editor plus live windows that
are the same page at `/?live=…` (offline from the same cached shell), opened
`noopener` over each display with the Window Management API's coordinates.

Why pages of their own rather than about:blank popups the editor draws into: a
live window then survives the editor tab being reloaded, discarded or closed, a
reload of the window itself comes back the same (source and scaling are in its
URL), and several moving windows aren't all drawn on the editor's one thread.
The cost is a protocol: state through localStorage `storage` events, the picture
through a BroadcastChannel after IndexedDB has it, status and commands over a
second channel.

What the browser won't do: more than one `window.open` per click (so a click
per display unless pop-ups are allowed), and full screen without a click in that
window. Chrome's fullscreen-popup origin trial (119–122) would have done both
from one click; it was dropped in March 2024 for "fullscreen without a gesture",
which is only for isolated web apps and enterprise policy.

Sound for AV sync: one window (the first opened) plays the loop. A looping
buffer would drift with the audio device's clock, so each pass is started
separately at the computer's-clock time of its start, mapped through
`getOutputTimestamp`; the seam is in AV sync's quiet half second. Tested against
a pretend device 80 ppm fast: every pass within 0.2 ms. Not measured: what the
browser adds to the picture or the sound on the way out.

Verified: in the app's browser pane (Chromium, 2048 × 1536 window) the live canvas
held a 1-pixel checkerboard exactly at 1:1, followed pattern, source, scaling and
picture changes, and moving patterns drew in about 1 ms a frame and ran at the
display's refresh whenever the pane was visible. In headless Chrome 155 with a
laptop screen and two pretend projectors (`scripts/live-check.mjs`), every check
in that script passes: listing, matching outputs to displays by size, one window
per click reported, placement over each display, full screen on it at its raster,
wake lock held when allowed, closing from the editor.

Not run: a real second display, Edge, Safari or Firefox's fallback path, the
desktop launcher's copy, and anything measured at the cable (colour management,
latency).

An independent review before landing found eight problems, all fixed:
`performance.timeOrigin` differs between processes after a Mac sleeps, so
windows opened either side of one disagreed (now `clock.ts`); a window that
opened and later closed was then reported as "didn't open"; display rasters
at fractional scaling were matched exactly (now within a pixel or two, shown as
"about"); a slow picture decode could overtake a newer one; every `storage`
event rebuilt every object and redrew huge scaled stills (now unchanged parts
keep their identity and stills draw once a frame); changes saved before the
live window started listening were missed; "sound on" outlived a suspended
AudioContext; rearranging displays lost track of live windows (now matched by
the display name the window reports). Plus nits: mute now survives a reload,
one wake lock at a time. Left as it is: a Close from one editor tab also
reaches windows another tab opened.

Fixing the second one turned up another: a `bye` posted from `pagehide` after
`window.close()` never arrived, so closed windows sat in the list until the
timeout. A window asked to close now says goodbye first. Raising the wait for a
new window to report from 3.5 s to 6 s greyed out Go live for 6 s after each
blocked window, so it's 2.5 s, and a display with something live on it is
never reported as not opened.

## 2026-10-25 — idle patterns: Idler's screensavers

Allan asked for the effects from Idler (`~/Projects/resolume/idler`, the Windows 95/98
screensavers as a Resolume generator) in a new pattern category, "Idle". All eleven are
here, each its own pattern, starting as Idler's first eleven presets have them.

Where the code came from: Idler's browser demo (`demo/plugin.js`) is a hand port of its
C++ savers, checked there against the C++ by `demo/tools/check_geometry.mjs`. Mine is a
TypeScript translation of that port, under `src/patterns/idle/`, with the two scene
shaders copied from `source/Shaders.cpp`. `scripts/check-idle-port.mjs` re-checks both
against an Idler checkout: shader text identical, and with the loop fitting off every
saver's mesh, camera and fog within 3e-15 of Idler's at 0, 11.5 and 37.25 s.

Decisions:

- **WebGL2, not the 2D canvas.** The 3D savers cross themselves (pipes through their
  elbows, bricks 1.5 mm proud of their mortar) and need a depth buffer. A painter's sort in
  2D would have been a third implementation and still wrong where triangles cross. The GL
  canvas is drawn into the pattern's 2D context, so preview, export, MP4, tiles and live
  windows didn't change. Resolution comes from the context's transform.
- **Pieces by cropping the projection**, at most 2048 px a side (a 4x multisampled 8K
  canvas would be over a gigabyte). The same crop makes a spanned output a window onto
  the surface.
- **Rates fitted to the loop.** Idler's savers are pure functions of time but not
  periodic. Every rate is rounded to whole cycles per loop (`fit`); families that must
  stay different are rounded up or down by a hashed chance (`fitSpread`), or every
  Mystify corner on a 10 s loop would make exactly one trip; slow camera orbits that
  would be forced to a whole turn sway instead (`orbit`). Curves and Colors needed more:
  Idler keeps its ratio off a whole number so the figure precesses forever, so here the
  precession is measured from the drawing head and its drift fitted separately. Any one
  frame is a figure Idler draws.
- **Pipes and Maze restart once a loop.** Replay makes them pure, not periodic, so each
  loop is one run from the seed. The restart is at 40% (Pipes) and 50% (Maze) of the loop
  so the still at 0 s is well into a run. Pipes just clears, as the original did when
  full; the maze fades out and in over half a second, because a jump to another corridor
  looks like a broken file.
- **Speed 0 holds the frame at t = 0**, not saver time zero, so a stopped 3D Pipes isn't
  an empty box, and `isAnimated` is false for it.

Verified: 79 new tests (periodicity mesh for mesh at four loop lengths and speeds,
replay played vs jumped, the marquee across its seam on wide surfaces, the clock, the
crop maths). In the app's browser pane: all
eleven render through `renderOutputTo`; a 3840 x 1080 output against two spanned

Not run: Safari, Firefox, Edge; a tiled (over 4096 x 2304) export of an idle pattern; the

An independent review before landing found three real problems, all fixed:

- Scrolling Marquee's copies only ran from one repeat left of the entry point rightwards,
  and everything right of the entry point is culled, so on a surface wider than the repeat
  (a span, a long strip, short text) the leftmost visible copy vanished every time the
  scroll wrapped, and fitting puts a wrap on the loop's seam. Idler has the same loop and
  the same gap on a wide composition. Now the copies reach the left edge, drawn left to
  right so a copy keeps its place in the mesh when the wrap renumbers it.
- A context loss could latch "no WebGL2" for the page's life (a GPU process restarting
  hands out contexts already lost, and the shader compile threw). Now it retries, falls
  back to a DOM canvas (Safari 16.4–16.x has OffscreenCanvas without WebGL2), and a loss
  during a draw is reported: the export stops instead of encoding notices. Checked by
  hand with `WEBGL_lose_context`: the next frame draws on a fresh context.
- Mystify's and Beziers' trails and the starfield's streaks were fixed seconds of saver
  time, and fitting makes a slowed saver's rates faster in saver time, so at a low speed
  the trail grew to the whole path. They're now Idler's share of a cycle (`behind`).

Quirks kept from Idler: Speed's centre is 0.94x, not 1 (its dead zone shifts the curve);
the maze stands still for its first cell after a restart (Idler's reset puts the
previous cell on the current one).

## 2026-10-25 — endless, for live output

Allan asked for an option on the generative cards (Idle, and the moving Halloween and
novelty ones) to run "live only": endlessly generated, so live output never repeats, with
an MP4 either refused or a short slice of the endless run. He chose the slice, "never
repeats" (whatever comes round comes round new), and one switch.

How it works:

- **`animation.endless`**, one switch under Loop, offered when `canRunEndless` (a generative
  pattern that moves; never AV sync, which is a measurement). `endlessOn` puts it in the env.
- **The clock** is seconds since 2026-01-01 on the shared clock (`endlessTime`), for the
  preview and every live window alike, so a span agrees as the looping windows do with the
  time modulo the loop. Seconds since 2026 rather than 1970 keep phases exact for decades.
- **Nothing fitted:** `cyclesPerLoop(natural, endless)` where `wholeCycles` was; small
  ambient motions through `freeCycles`, a little off their whole number each.
- **New each time round:** anything that laps the world is drawn from `lapX` (unwrapped)
  with `eachRepeatIndexed`, whose `k` stays the same all the way across, and its looks are
  seeded from `k`; launches, puffs, sea bands, dances and the ghost's visits from
  `lapNumber`, changing only where they can't be seen. Pipes and Maze run in
  `ENDLESS_RUN_SECONDS` (120 saver seconds) runs from `runSeed`, so a replay is one run.
- **The MP4** of an endless pattern is a slice from the PNG's moment (`stillTime`, unwrapped),
  `_slice.mp4`, and the manifest says it doesn't loop.
- **Loop mode untouched:** every slot draws its random numbers in the same order either way.

Bitten: the sea's waves travel at a speed that depends on a band's depth, so timing them by
the clock spun them faster every year (a depth-dependent rate times t of 3e7); they're timed
by the band's own age. The review found the scroll's far herd sliding at Speed 1 (the layer
scrolls 0.7 widths a loop endless, against the herd's drift of -1; drift is now the loop's
walk less the scroll), ambient motions still periodic, skeletons with nothing to vary (they
now pick zombie or skeleton per crossing) and stars on the same rays. Left as it is: the
seven bats circling the haunted house's spire are the same seven, at unfitted rates, since
changing one mid-orbit would show.
