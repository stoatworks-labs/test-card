# AGENTS.md — Test Card

LLM onboarding. Read this before changing anything. [CLAUDE.md](CLAUDE.md) is the
short command reference.

## What this is

A browser-only React/TS/Vite SPA that turns a show's output map into test
pattern PNGs. No backend. Deployed as a **Cloudflare Worker serving static
assets** — *not* a Pages project (see `wrangler.toml`; the fleet does not use
Pages, and `pages_build_output_dir` fails in a way that reads like a missing
build step).

Sibling projects, both of whose export formats this reads:
`~/Projects/video/blend-calc` and `~/Projects/video/pixel-peeker`.

## The shape of it

The unit of work is an **`Output`**: one physical video output with a raster in
pixels. Importers turn a file into `Output[]`; patterns paint into a canvas whose
coordinate space is that raster; exports name and pack the results. Nothing else
is load-bearing.

## Invariants — do not break these

**1. Geometry is pure; canvases are dumb.**
`rp219Layout()` and `gridLines()` return numbers and are unit tested. The canvas
layer only fills rectangles. Do not move layout maths into a painter — it becomes
untestable the moment it needs a `CanvasRenderingContext2D`.

**2. Bar colours are computed, never tabulated.**
Everything except +I and +Q comes from an R′G′B′ definition through
`rgbToYcbcr`. All fifteen computed values were verified to land exactly on the
measured ffmpeg ones. If you find yourself pasting a Y′CbCr triple, stop — the
only legitimate constants are `plusI` and `plusQ`, which are not colours and
cannot be derived.

**3. `layOut()` accumulates in exact fractions and rounds once.**
This is why bands always tile the raster with no gaps and no overlap, and why the
last boundary is pinned to the total. Rounding each segment independently
reintroduces drift and a visibly narrow final column.

**4. Never invent an output's raster silently.**
Every `Output` carries `rasterSource`. `slice-bounds` means *guessed* and must
stay badged in the UI, warned about on import, and listed in the ZIP manifest. An
output that is the wrong size produces a pattern that looks perfect and is
useless on site.

**5. The preview calls the same painters as the export.**
`Preview.tsx` must go through `renderOutputTo`. An earlier version had its own
copy of the overlay code and the two had already drifted — the export drew a
border round the burn-in plate and the preview did not. A preview that
reimplements the thing it previews is worse than no preview.

**6. Do not vendor the sibling projects' libraries.**
Pixel Peeker's cabinet library and Blend Calc's projector library stay where they
are. Importing a file that needs them is refused (Pixel Peeker project) or asks
the user (Blend Calc raster). A vendored copy drifts and then produces confidently
wrong tile sizes.

**7. Artwork is geometry too.**
A banana, a dinosaur or a mountain range is a list of polygons from a pure
function, built in real units (millimetres for the banana, metres for the
dinosaurs). The tests hold them to their sizes: each dinosaur within 3.5% of its
quoted length and 6% of its stated height, the banana 190 mm along its curve. If
you change a drawing, run the tests as well as looking at it: a nicer-looking
Tyrannosaurus that is 14 m long is a regression. When you convert shapes between
units with `mapShapes`, pass the scale as `strokeScale` as well, or a 1.2 mm
stroke becomes 1.2 m.

**8. Moving patterns are periodic in the loop, exactly.**
Everything that moves does a whole number of cycles in `loopSeconds` (use
`wholeCycles` and `phase`), and everything that scrolls moves a whole number of
its own periods. Frame N must be pixel-identical to frame 0 — that is what makes
the MP4 seamless — and the tests check it for the sea, the layers and the
hamsters. A speed slider that produces 3.4 cycles per loop is a seam once a
loop, forever.

**9. No `Math.random` in `src/patterns/`.**
A pattern is a function of its settings, its output and the time. Use the
seeded generator in `random.ts`. The preview and the export must agree, frame N
must be the same every time it is asked for, and two outputs of one span must
agree on where the trees are. Draw every random number for a thing BEFORE
skipping it as off-screen: a `continue` ahead of the draws makes the sequence
depend on where the canvas sits, and the volcano grew a different forest on
each output until review caught it.

**10. MP4 colour is converted here, never by the encoder.**
`rgbaToI420` applies Rec.709 into limited-range 4:2:0 and the file's `colr` box
says so. Handing the encoder RGBA leaves the matrix to the browser — the same
trap as ffmpeg's rgb24 below. The level range is honoured: `canvasRange()` says
whether the canvas holds 0–255 or 16–235 codes, and only the measurement
patterns that follow the level setting can be legal range; artwork is always
full.

**11. On a span, surface things go on the surface.**
With "carry on across outputs", the scale and novelty patterns are drawn in
composition coordinates and each output is a window onto them. Rulers, labels,
captions and the size readout are placed on the SURFACE's edges and centre, so
two projectors blending over each other draw the same pixels in the overlap
(measured: at most nine antialiased edge pixels differ across the Blend Calc
fixture). Facts about one output — "pitch assumed" — stay on that output.
Sample curves on a grid anchored to the world (or, for something that scrolls,
to the thing itself), not the canvas, or the antialiasing differs at the join
and a scrolling peak shimmers. LED tiles are NOT surface things: they belong to
the output that drives them and start at its own origin. An output whose
composition region has a different aspect from its raster is not spanned at
all (`spanPlace`); on a stretched mapping nothing is life-size both ways.

**12. A live window reads the editor's state and never writes it.**
Live windows (`/?live=…`, `LiveView`) are pages of their own, opened `noopener`.
They take outputs and settings from the localStorage the editor already writes
(`followSavedState`) and the picture from IndexedDB (`onImageChanged`), and
draw through `renderOutputTo` / `renderCompositionTo` like the preview (rule 5).
They must not call a store action that persists: a live window holding an old
copy would write it back over the editor's. What one shows and how it scales
live in its URL, so a reload of the window comes back the same; the editor
steers them only over `channel.ts`. "1:1" is only claimed when the canvas, sized
in device pixels from `devicePixelContentBoxSize`, is the raster's size.

## Traps that have already cost time

**A page gets one pop-up per click, and full screen only from a click in that
window.** Chrome consumes the click's activation on the first `window.open`, so
"Go live" on three displays opens one window; the panel reports the others as
not opened after `GONE_MS` and the next click opens the next. With `noopener`
`window.open` returns null either way, so a window is only known to have opened
when it reports in. `requestFullscreen` checks activation on the element's own
frame, so the editor can't do it for a window; the live window's own click does.
The "fullscreen popup" origin trial that would have fixed both was dropped.

**The display list needs Chromium, a secure context and a permission.**
`getScreenDetails` is absent on plain http, which is how the desktop launcher's
copy is reached from another machine; the panel falls back to "Open a live
window" and drag. The app's own browser pane (Electron) refuses the permission
and opens `window.open` in the same tab, so it can test a live window but not
placement: use `scripts/live-check.mjs`, which runs headless Chrome with
`--screen-info` pretend displays. `--screen-info` sizes are device pixels.

**A cut-short live-check leaves its Chrome running on port 9333**, and the next
run would talk to it, with the old displays. The script refuses to start if the
port answers; kill the old one (its profile is in the temp folder).

**`performance.timeOrigin` is not a shared clock.** Each renderer process fixes
its own wall-clock anchor, and a Mac's monotonic clock stops while it sleeps, so
two live windows opened either side of a sleep (or a clock step) disagree by
that long. Live windows time everything with `unixMs()` from `clock.ts`:
`performance.now()` plus an offset to `Date.now()` re-taken every second.

**A `bye` posted from `pagehide` after `window.close()` gets lost.** A window
asked to close says goodbye first, then closes. One closed by hand does get its
`pagehide` goodbye through (live-check tests both).

**Live colour is managed, the files' isn't.** The browser and the OS colour-manage
the canvas to the display's profile, so live code values on the cable needn't be
the PNG's. Not measured; the guide sends level checks to the files.



**ffmpeg's `rgb24` output uses the wrong matrix.** `smptehdbars -pix_fmt rgb24`
converts HD content with BT.601 and renders 75% yellow as (189, 202, 7) instead
of (191, 191, 0). Use the Y′CbCr planes and apply Rec.709 yourself. Full
workings in [docs/rp219.md](docs/rp219.md).

**And its default chroma upsampling smears band edges.** Without
`-sws_flags neighbor`, converting to `yuv444p` interpolates: row boundaries move
by ~3px and edge colours come back close-but-wrong.

**macOS `unzip` is Info-ZIP 6.00 from 2009 and ignores the UTF-8 flag.** It
transliterates non-ASCII names for display and then refuses to extract them at
all with "Illegal byte sequence", regardless of `LC_ALL`. That is the binary, not
the archive. `zip.test.ts` verifies UTF-8 names with Python's `zipfile` and uses
`unzip` only for ASCII round-trips.

**An empty ZIP makes `unzip -t` exit 1.** "zipfile is empty" is a warning about
content, not a structural complaint, so `execFileSync` throws on a perfectly
valid archive.

**Browsers return a blank canvas over the size limit, they do not throw.** An 8K
wall would export a folder of empty PNGs that look fine in a file listing.
`canvasLimitProblem()` checks before drawing and the UI refuses. Do not remove it.

**Blend Calc does not persist its solved overlap.** In `fit-width` the vertical
overlap is computed, displayed as "(solved)", and never written back to the
project — so the value in the JSON is a stale input from some other mode. The
importer flags the affected axis rather than reading it.

**Canvas strokes straddle the path.** A 1px line on an integer coordinate renders
as two grey rows. `crispLine()` offsets by half a pixel for odd widths; this
matters more here than in most drawing code, because the point of an alignment
pattern is that 1px is exactly 1px.

**Chrome's H.264 rate control codes the first frame of a stream differently.**
In a loop the first frame is the seam. `encodeLoop` encodes the loop's last
second first, throws it away, and starts the loop proper on a forced keyframe.
A fixed quantiser (`bitrateMode: 'quantizer'`) fixed it too, but in Chrome 152
on a Mac it fell back to the software encoder and ran ten times slower.

**Chrome's encoder refuses odd rasters and anything over 36 864 macroblocks.**
4:2:0 needs even sides. Chrome 152 on a Mac takes H.264 up to 36 864 16x16
macroblocks a frame, counted after padding, whatever the shape and at 60 fps
too: level 5.1's MaxFS, 4096 x 2304 (measured with `isConfigSupported`,
2026-10-20: 8192x1080 and 2304x4096 yes; 4096x2306, 4112x2304 and 4080x2312,
fewer pixels but more macroblocks, no), on High, Main and Baseline, hardware or
software alike. HEVC, VP9 and AV1 said yes at 8K, but mp4.ts only writes H.264.
So `planLoop()` cuts a bigger raster into tiles before frame 0 and
`encodePlan()` encodes them one after another. Never let it fail at frame 900.

`planLoop` asks the browser, not a table, in this order: the whole raster on
every profile; if refused, the same at auto bitrate (a hand-set bitrate the
encoder won't take is an error, not a reason to tile); a 640x360 probe (a
browser with no H.264 at this frame rate is an error, not a reason to ask
about every grid); then grids, on the probe's profile alone, skipping any
whose tiles are no smaller both ways than a size already refused. Before
those, it asked up to 793 questions for a raster nothing fits; now 265.

**A video tile is the whole picture shifted, not a crop.** `encodePlan` draws
each tile by translating the full raster's render under a canvas the size of
the tile. So a painter must never read the canvas's size, and anything that
resets the transform must keep the translation, as `drawBrokenWall` does with
`setTransform(1, 0, 0, 1, m.e, m.f)`. Tile edges and offsets are even, so each
tile's 2x2 chroma blocks are the whole raster's. The cost is drawing the whole
picture once per tile per frame; the broken wall builds a full-size offscreen
canvas each time, so a tiled broken wall is slow. Checked by decoding an 8K
loop's four tiles, stitching them and comparing with `renderOutput`: mean
|error| 0.54 code values, the seams no worse than elsewhere.

**A hidden tab's timers run once a second.** Chrome throttles `setTimeout` in a
background tab (to once a minute after five minutes), so an encode loop that
yields with it turns a 300-frame export into an hour when the user tabs away.
`encodeLoop` yields with a `MessageChannel` instead, for pacing and for
back-pressure alike. (Waiting on the encoder's `dequeue` event loses a race
when it fires before the listener is attached.) Measured: the same loop takes
the same time behind another tab as in front. A minimised window is untested.

**A loop is held whole in memory.** Every encoded frame stays until the file is
written, then is copied into the MP4 and again into the download. `encodeLoop`
refuses anything estimated over `MAX_LOOP_BYTES` (1 GiB) before frame 0, and
`planLoop` counts every tile of a tiled loop against the same limit, and the
export adds up every loop going in one ZIP (tiles made 8K outputs possible, and
three of them at 1 GB each would otherwise be built and then die): the finished
files are all held until the ZIP is built.

**AAC primes, and AVFoundation trims it twice unless told not to.** An AAC encoder starts with
priming samples: 2112 (44 ms, more than a frame) from Chrome on a Mac, 1024 from ffmpeg's. The MP4
skips them with an edit list (`elst` media_time = the priming), and `encodeLoopAudio` measures the
priming every time by sending a click through and finding it again, rather than trusting a number.
But AVFoundation, which Resolume plays through on a Mac, ALSO trims the priming itself unless the
track has the `roll` sample group (`sgpd`/`sbgp`, roll distance -1) that Apple's own encoder writes:
without it the sound played 2112 samples early in AVFoundation and on time in ffmpeg. Found by
disabling that group in an `afconvert` file, which then went early too. Keep both boxes, and check
any change to the audio track in both players (`scratchpad`-style: decode with ffmpeg, read with an
AVAssetReader), not one.

**The edit must end on a packet boundary, exactly.** AVFoundation stops at the edit's end to the
sample; ffmpeg keeps the whole packet the end falls in, so a file it loops gained the rest of that
packet every time round (15 ms a loop at 29.97). `alignToPackets` puts silence in front so priming,
padding and loop end on a boundary, and with sound the movie timescale is the sample rate: in
milliseconds the duration rounded, and rounding up past a boundary pulled in a whole extra packet.
`mp4.test.ts` loops the fixture through ffmpeg three times to hold both.

**Dead trees are cached as `Path2D`s.** A Halloween dead tree is a few hundred polygons and
never changes, so `drawTree` builds it once at its own origin, keyed by seed, size (to a quarter
pixel) and forking depth, and fills it in one go. Every polygon is wound the same way first
(`wound`), because one nonzero fill of overlapping subpaths wound opposite ways punches holes
where they cross. Anything that changes a tree's shape must be in the key.

**Anything that crosses a Halloween scene does one lap per loop, and a lap is not the world.**
`walkLap` is the world's width up to about one and a half 16:9 screens, and 1.3 screens beyond
that, for the walkers, witches, vampires and bats alike: crossing a six-projector span once per loop
is a sprint. It is deliberately not a whole number of outputs (a lap of exactly one output width
gave every output the same six zombies in the same poses). Strides are fitted to the lap like the
dinosaurs' are, and a zombie's lurch is periodic in its stride, so it still does exactly one lap.

**Per-tile things on a span are keyed on where the tile is, not its column.** LED tiles start again
at each output's origin, so a pumpkin keyed on `(col, row)` gave every output of a span the same
patch, flickering in step (review, 2026-10-21). `tileKey` hashes the tile's surface position, as
the broken wall's `assignFaults` does.

**The logo is traced, not drawn.** The only Stoatworks mark there is is a 400 x 310 PNG, which
goes soft in the middle of a 4K card, so `scripts/trace-logo.py` splits it into bowtie, fill and
outline masks, upsamples and blurs them a little (the raster's wobble otherwise traces as a wobbly
outline) and runs potrace on each. Thresholding at the source size first gave stair-stepped edges,
and taking every light pixel as fill gave a white fringe outside the outline: the fill is
"everything the outline encloses", found by flooding in from the border. Path2D takes the SVG path
strings as they are.

**Vite caches a dynamically imported module across edits.** Driving the encoder
from the browser console with `await import('/src/lib/video.ts')` keeps handing
back the version from before your last edit until the page is reloaded. Two
"different" runs that produce byte-identical files are the giveaway.

## Embedded elsewhere

**LivePremier Plus draws these patterns on a switcher.** Its `tools/sync-test-card.mjs`
bundles `src/engine.ts` with this repo's own rolldown into its
`src/vendor/test-card/engine.js`, recording this repo's commit and a SHA-256 of every
source file that went in, so its tests can tell a deliberate sync from drift. It builds
`Output`s from the switcher's own output and canvas geometry and puts the PNGs on the
switcher as stills. So `engine.ts` is an interface: `engine.test.ts` holds its import
graph clear of React, the store and the UI, and a rename there breaks the next sync
there rather than anything here. A pattern added here reaches LivePremier Plus only when
it re-syncs.

## Testing

`npm test` — 454 tests, all offline. ffmpeg is **not** required: the RP 219
reference is committed as JSON, and the MP4 tests that ask ffprobe and ffmpeg
to read a muxed file skip when they are not installed (they run on this Mac).
The H.264 they mux is a committed libx264 stream, regenerated with
`scripts/make-h264-fixture.sh`.

The importer suite runs against real files in `test/fixtures/`, none of them
hand-written:

- `resolume-arena-preferences.xml` — Arena 7.27.0's own `AdvancedOutput.xml`
  from this machine (a DeckLink output, so the raster must be inferred)
- `resolume-arena-preset.xml` — a real saved Advanced Output preset
- `blend-calc-export.xml` — `BLEND_CALC_XML_OUT=<dir> npx vitest run resolume`
  in `~/Projects/video/blend-calc`
- `pixel-peeker-export.xml`, `pixel-peeker-interchange.json` —
  `PP_WRITE_ARTEFACTS=<dir> npx vitest run export` in `~/Projects/video/pixel-peeker`

If you change an importer, regenerate the fixture from the sibling project rather
than editing the XML by hand.

`test/recording-context.ts` is a pretend 2D context that records every fill,
stroke and text in device space, with the transform and save/restore stack kept
as a canvas keeps them. `halloween.paint.test.ts` uses it to check that the
painters draw the same at the end of the loop as at the start, the same on each
output of a span as on the whole surface, and leave the context as they found
it. It doesn't rasterise: a match means the same geometry, not the same pixels.

## Not doing, on purpose

- **No `diag` module.** Static browser page; nowhere for a rotating log to go.
  Same call as blend-calc.
- **No ZIP64.** Capped at 4 GiB and 65535 entries, and `buildZip` throws rather
  than emitting a corrupt archive. Test patterns will not come close.
- **No compression in the ZIP.** PNGs are already DEFLATEd; store-only saves a
  dependency and buys ~0%.
- **No releases or installers.** This repo exists to feed the deployed app, like
  blend-calc and pixel-peeker. Its absence from the fleet's download tooling is
  the design, not a gap.
